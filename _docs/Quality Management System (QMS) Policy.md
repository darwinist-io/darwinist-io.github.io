# **Quality Management System (QMS)** 

## **Utilization of GitHub as the Comprehensive Quality Management System for ISO 13485 Compliance**

### **1\. Purpose**

This policy defines the use of GitHub as the organization’s complete Quality Management System (QMS) for compliance with ISO 13485\. It establishes how GitHub is used to manage documentation, design controls, change controls, records, approvals, and all quality-related processes.

### **2\. Scope**

This policy applies to all personnel involved in the design, development, maintenance, release, or support of medical device software within the organization. All QMS-related documentation and records are created, reviewed, approved, maintained, and stored within GitHub.

### **3\. QMS Structure in GitHub**

GitHub serves as the centralized platform for all quality and regulatory activities, including:

* Quality Manual  
* Standard Operating Procedures (SOPs)  
* Work Instructions (WIs)  
* Controlled templates and forms  
* Design History Files (DHFs)  
* Device Master Records (DMRs)  
* Risk management files  
* Verification and validation documentation  
* Software development lifecycle records  
* Issue tracking and change requests  
* Release records

### **4\. Document Control**

All controlled documents are maintained in designated GitHub repositories using markdown as the text format. Document control is achieved through:

* Branch protection settings  
* Pull request (PR) workflows for review and approval  
* Versioning through commit history and tags  
* Permanent record retention through immutable commit logs  
* Markdown or PDF-controlled documents stored within the repository structure

Each controlled document includes:

* Unique document identifier  
* Version number  
* Revision history  
* Approval signatures recorded via PR approvals

### **5\. Design and Development Controls**

Design controls are implemented within GitHub using:

* Repository structure representing design inputs, design outputs, architecture, and specifications  
* Issues and pull requests to document design changes, discussions, and reviews  
* Labels and project boards to categorize design stages  
* Traceability established through linked issues, commits, and PRs  
* Maintenance of the DHF within the repository for each regulated product

### **6\. Change Control**

All changes to controlled documents, design artifacts, or software code are managed exclusively through pull requests.

Each pull request serves as a formal change record and includes:

* Description of the proposed change  
* Linked issues, requirements, or risk items  
* Review and approval by authorized personnel  
* Automated checks, tests, and validations  
* Evidence of verification activities

Merging a pull request constitutes formal approval of the change.

### **7\. Risk Management**

Risk management files are maintained within GitHub repositories and updated using controlled PR workflows. Risk assessments, mitigations, verification of controls, and traceability are maintained through:

* The risk management directory  
* Issues linked to risk items  
* Pull requests documenting updates to risk analyses

### **8\. Software Development Lifecycle Management**

GitHub is used as the system of record for all software lifecycle activities, including:

* Requirements management  
* Architecture and design documentation  
* Implementation and code reviews  
* Verification and validation evidence  
* Release notes and version tagging  
* Continuous integration and testing records

### **9\. Training Records**

Training records are documented within GitHub using designated repositories or tracked through issues and PR approvals associated with onboarding or procedural updates.

### **10\. Corrective and Preventive Actions (CAPA)**

CAPA processes are documented and executed using GitHub issues, linked pull requests, and dedicated repository sections. Each CAPA includes:

* Problem description  
* Investigation and root cause analysis  
* Corrective or preventive actions  
* Verification of effectiveness  
* Approval and closure via PR

### **11\. Internal Audits**

Internal audits are planned, executed, and recorded within GitHub. Audit findings, responses, corrective actions, and verification activities are documented as issues and resolved through pull request workflows.

### **12\. Management Review**

Management reviews are scheduled and documented within GitHub, including:

* Meeting agendas  
* Inputs and outputs  
* Action items  
* Attendance records  
* Approval of review minutes

### **13\. Access Control**

GitHub access permissions determine authorization levels for reading, editing, reviewing, or approving controlled documents and changes. Role-based access is managed using GitHub’s built-in user and team management features.

### **14\. Record Retention**

All QMS records are retained permanently within GitHub. Commit histories, issues, pull requests, and release tags serve as immutable records of activity and compliance.

### **15\. Continuous Improvement**

The QMS maintained in GitHub is continually improved through:

* Feedback from internal audits  
* CAPA processes  
* Management review  
* Stakeholder feedback documented through issues and pull requests

---

This policy establishes GitHub as the fully integrated platform for managing the organization’s Quality Management System in alignment with ISO 13485 requirements.
